# AGENTS.md — инструкции для AI-агентов

Сначала прочитай [CONTRIBUTING.md](CONTRIBUTING.md): контекст проекта, модули, границы, стиль кода, тесты, правила commit/PR.  
Пользовательская документация: [README.md](README.md).  
Task-specific правила Cursor: [`.cursor/rules/`](.cursor/rules/).

## Формат ответа

Обязательный порядок:

1. **План действий**
2. **Изменения в коде**
3. **Пояснение решений**
4. **Шаги проверки**

## Commit и PR

В теле commit message и в описании PR всегда включай строку:

```text
Сделано с агентом, проверено человеком
```

## Когда спрашивать

Спроси перед изменением публичного API core, семантики lock, зависимостей BOM/core или схемы существующего store.  
Для нового provider по образцу соседнего модуля и локального багфикса/рефакторинга опирайся на CONTRIBUTING и соседний код.

## Антипаттерны ShedLock

Детали — в README; здесь — то, что агент не должен «улучшать» по ошибке:

- Не трактуй lock как очередь: при занятом lock задача **пропускается**, не ждёт.
- Не удаляй lock-row/document вручную из store (у ShedLock есть кэш существующих строк; поведение станет непредсказуемым).
- `lockAtMostFor` — safety net при падении узла, не «желаемое время работы». Слишком короткое значение → возможны параллельные holders.
- Не превращай проект в distributed scheduler.
- Не полагайся на рассинхронизированные часы app-серверов без `usingDbTime()` (или аналога) и достаточного `lockAtLeastFor`.

## Типовые сценарии

### 1. Добавление новой базы (lock provider)

**Пример промпта**

```text
Добавь LockProvider для <StoreName>. Следуй CONTRIBUTING.md и правилу shedlock-new-provider.
Сделай модуль, IT-тесты и секцию в README.
```

**Ожидаемый формат ответа**

1. План: путь модуля, зависимости, эталонный provider, список файлов.
2. Код: `LockProvider` (+ `SimpleLock` при необходимости), `pom.xml`, регистрация в корневом `pom.xml`, IT, документация.
3. Пояснение: как устроен acquire/release, время (app vs store), отличия от эталона.
4. Проверка: `./mvnw -pl providers/<store>/shedlock-provider-<name> -am test`.

**Критерии готовности (DoD)**

- [ ] Модуль под `providers/<store>/shedlock-provider-*`
- [ ] Реализация `LockProvider`, стиль как у соседних providers
- [ ] IT на базе `shedlock-test-support`
- [ ] Модуль подключён в корневом `pom.xml`
- [ ] Секция в README
- [ ] Тесты модуля зелёные
- [ ] В commit/PR есть `Сделано с агентом, проверено человеком`

### 2. Багфикс

**Пример промпта**

```text
В <модуль/класс> баг: <описание>. Минимальный fix + регрессионный тест.
Следуй CONTRIBUTING.md и правилу shedlock-bugfix.
```

**Ожидаемый формат ответа**

1. План: гипотеза причины, затронутые файлы, какой тест добавится.
2. Код: минимальный diff + тест, воспроизводящий баг до фикса.
3. Пояснение: root cause и почему fix безопасен для семантики lock.
4. Проверка: `./mvnw -pl <module> -am test`.

**Критерии готовности (DoD)**

- [ ] Diff минимальный, без побочного рефакторинга
- [ ] Есть регрессионный тест (или обоснование, почему тест невозможен)
- [ ] Публичный API и семантика skip-not-wait не изменены без запроса
- [ ] Тесты модуля зелёные
- [ ] В commit/PR есть `Сделано с агентом, проверено человеком`

### 3. Рефакторинг без изменения поведения

**Пример промпта**

```text
Отрефактори <область> без изменения поведения и публичного API.
Следуй CONTRIBUTING.md и правилу shedlock-refactor.
```

**Ожидаемый формат ответа**

1. План: что улучшается (читаемость, дублирование), что гарантированно не меняется.
2. Код: только рефакторинг, без «улучшений» семантики.
3. Пояснение: почему поведение эквивалентно.
4. Проверка: те же тесты затронутых модулей — `./mvnw -pl <module> -am test`.

**Критерии готовности (DoD)**

- [ ] Публичный API не изменён
- [ ] Семантика lock (skip-not-wait, TTL) не изменена
- [ ] Нет попутных багфиксов/фич
- [ ] Существующие тесты зелёные
- [ ] В commit/PR есть `Сделано с агентом, проверено человеком`
